# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dayform is a local-first weekly planner. The product is the Expo SDK 57 app in `packages/mobile`. The repo is a Bun + Turborepo monorepo generated from a Runable template, so `packages/web` (Vite + Hono + oRPC + Drizzle) and `packages/desktop` (Electron shell around web) are template scaffolding that the app does not use for task storage. Don't build features there unless asked.

## Commands

Run from the repo root unless noted. Bun is the package manager (`bun@1.3.14`).

```bash
bun install --linker hoisted        # hoisted linker is required; Metro resolves from root node_modules
bun run typecheck                   # turbo → tsc --noEmit in each package
bun run lint                        # runkit lint (oxlint); lint:fix to autofix
bun run build                       # turbo build (web: tsc + vite build)
```

- **Run the mobile app locally:** `cd packages/mobile && bunx expo start`. The root `bun run dev:mobile` only works inside Runable: `scripts/start-mobile.ts` throws unless `EXPO_PACKAGER_PROXY_URL` is an `https://` URL.
- **Tests:** `cd packages/mobile && bun test` (`bun test lib/tasks-store.test.ts` for one file, `--coverage` for coverage). They cover the framework-free modules in `lib/` (`planner`, `task-storage`, `tasks-store`, `timeline-layout`). There are no component/UI tests, so screen changes need manual verification. Keep logic that needs tests out of React files and in those pure modules.
- **Typecheck:** mobile's `typecheck` runs two programs: `tsc --noEmit` for the app (`tsconfig.json`, `"types": []`, test files excluded) and `tsc --noEmit -p tsconfig.test.json` for `lib/**/*.test.ts` (adds `bun` types). Don't put `bun`/Node types in the app program: they make `setTimeout` return `Timeout` instead of `number` and clash with `__env.d.ts`'s `process`. Root and web use TypeScript `7.0.1-rc`; mobile uses `~6.0.3` (TS 6 no longer auto-loads `@types/*`).
- The root `bun run lint` needs `@runablehq/runkit`, which a filtered install (`bun install --filter ...`) skips; do a full `bun install --linker hoisted` first.
- Expo Doctor warns about React 19.2.3 (mobile) vs 19.1.0 (web) in one monorepo. This is a known warning noted in `DOWNLOAD-README-VI.md`.

### Building an Android APK locally

`packages/mobile/android/` is generated and gitignored. It does not exist until you prebuild. `eas.json` has no `apk` profile, so EAS cloud builds produce AABs by default.

```bash
cd packages/mobile
bunx expo prebuild --platform android --no-install
cd android && ./gradlew assembleRelease     # → app/build/outputs/apk/release/app-release.apk
# faster, arm64 phones only:  ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a
```

**Windows path-length trap:** a build from a deep path fails in the native step with `ninja: error: ... Filename longer than 260 characters` (seen on `react-native-gesture-handler`'s codegen objects). A `subst` drive does NOT fix it (the path is still ~318 chars, and Metro cannot resolve `expo-router/entry` through a `subst` drive), and `CMAKE_OBJECT_PATH_MAX` doesn't help either (the build directory itself is too long). Instead, `packages/mobile/package.json` sets `expo.autolinking.exclude` for `react-native-gesture-handler`, `react-native-reanimated` and `react-native-worklets`, which the app doesn't use (expo-router only needs them for the opt-in `expo-router/js-stack`; this app uses `Slot` + `Tabs`). **Don't import those libraries or `expo-router/js-stack` without first removing them from that list and solving the long-path problem** (Windows long paths + a newer ninja/CMake, or build on Linux/EAS). The planned timeline drag-and-drop should use React Native's built-in `PanResponder` for this reason.

Needs JDK 17+ (21 works), `ANDROID_HOME` pointing to an SDK with platform 36 and build-tools 36.0.0 (Gradle auto-installs NDK 27.1 once licenses are accepted). A signed release needs `DAYFORM_KEYSTORE_PATH`, `DAYFORM_KEYSTORE_PASSWORD`, `DAYFORM_KEY_ALIAS` and `DAYFORM_KEY_PASSWORD` in the environment (`DAYFORM_REQUIRE_RELEASE_SIGNING=1` fails the build instead of falling back to the debug key); the key is not good for the Play Store as it is. With `expo-updates` the Gradle build is heavy: on Windows pass `"-Dorg.gradle.jvmargs=-Xmx3072m -XX:MaxMetaspaceSize=768m"` to `gradlew`, and stop a leftover Kotlin compile daemon (`java` running `kotlin-compiler-embeddable`) before `expo prebuild --clean`, or the clean fails with `EBUSY`. The Linux release workflow passes the same limits (`-Xmx4g`, `MaxMetaspaceSize=1g`), skips the `lintVital*` tasks and times the build step out after 30 minutes: without it an `OutOfMemoryError: Metaspace` in expo-updates' KSP step makes Gradle HANG until the 60-minute job limit instead of failing. **`.gitignore` trap:** the root rule `android` (for the generated app folder) matches every folder with that name, so `modules/dayform-widget/android/` (Kotlin, manifest, resources) needs the explicit re-include that is there now; a build from a fresh checkout would otherwise have no widget. On the original dev machine (Windows) the SDK lives at `D:\Android\Sdk` and `GRADLE_USER_HOME` at `D:\Android\gradle` because C: is nearly full, and `JAVA_HOME` in the user environment points to a nonexistent path and must be overridden per shell.

## Architecture

### Mobile app (`packages/mobile`)

Expo Router with file-based routes: `app/_layout.tsx` is the root and `app/(tabs)/` holds three tabs (`index.tsx` = Timeline, `explore.tsx` = Tasks with search/filters and the Settings section, `stats.tsx` = weekly/monthly Stats).

**Provider chain in `app/_layout.tsx`:** `ErrorBoundary` (own fallback screen; it sits outside the providers so it reads the stored language itself) → SafeArea → `SettingsProvider` → `ThemeProvider` → `LanguageProvider` → `CategoriesProvider` → `TasksProvider` → `UpdateProvider` (APK update check + popup) → `OtaProvider` (over-the-air content updates) → `<Slot />` plus the render-nothing helpers `NamePrompt` (first-launch name popup), `UndoBar`, `RemindersBridge` (syncs local notifications and the morning summary; never syncs while loading or writes are blocked), `NotificationActions` (Done / Snooze buttons and tap-to-open; only a validated `taskId` is ever read from notification data), `SeriesExtender` (tops up recurring tasks with *silent* `mutate`), `SnapshotScheduler` (weekly rolling local snapshots), `WidgetBridge` (feeds the home-screen widget) and `OtaAutoCheck`. An `AppReadyGate` holds the splash until theme, language, settings and categories have loaded. All Runable template code (analytics, oRPC client, web safe-area, `QueryClient`) has been removed from the app; `packages/web`, `packages/desktop`, `.runable` and the root scripts are untouched leftovers.

**Feature modules** (all pure and tested unless noted): `recurrence.ts` (recurring tasks are *materialised* as flat tasks sharing a `seriesId`, ids `${seriesId}:${date}`, ~8 weeks ahead; the 120 cap counts only future rows), `task-save.ts` (editor form → one `store.mutate` update; `allowedScopes`), `reminders.ts` (+ `reminders-expo.ts` adapter, Android channel `reminders-v2`), `timeline-gestures.ts` (drag/resize math + state machine; the PanResponder glue is in `hooks/use-block-drag.ts` and `components/timeline/drag-controller.ts`, untested), `backup.ts`/`backup-flow.ts` (import limits: 2 MB file, 1.5 MB stored list), `explore-groups.ts`, `shell-layout.ts` (tab bar = 58dp + bottom inset; UndoBar/FAB offsets), `theme-preference.ts`. Each feature keeps its Vietnamese strings in `lib/i18n/<feature>.ts`, registered in `lib/i18n/index.ts` and merged into `language.tsx`. Palettes live in `constants/palettes.ts` (re-exported by `constants/theme.ts`; tests import the former); use `useColors()` tokens, never hex literals (a contrast test pins known light-palette gaps). Native pickers/notifications mean Android needs `expo-notifications` and `USE_EXACT_ALARM` (without exact alarms Android may fire reminders up to an hour late).

More modules: `undo.ts` (safe undo: `mutate(update, { undo: "bulk" | "delete" })` records a per-task diff, and undo only reverts tasks that were not edited since), `archive.ts` (done tasks older than 90 days move to the separate key `dayform.archive.v1`, written *before* they leave the main list), `recovery.ts` + `snapshots.ts` (list/restore/delete the `backup`/`corrupt`/`snapshot` copies; deletion refuses any key outside those prefixes), `search.ts` (accent-insensitive, handles `đ`), `stats.ts`/`stats-chart.ts` (bars are plain Views, no chart library), `notification-actions.ts`, `carry-over.ts` ("Move to today" for unfinished tasks of a past day; series occurrences are excluded), `greeting.ts` (greeting and slogan by time of day), `duration-input.ts` (minutes/hours switch), `update-check.ts`/`update-state.ts`/`update-store.ts`. Recurrence supports `daily | weekdays | weekly | monthly` (month-end clamping from the first occurrence's day) and an optional `repeatUntil`; dragging a repeating task past its end date must go through `keepUntilValid`.

**Personalization (Personal tab, 4th tab):** `lib/settings.ts` + `settings-store.ts` + `settings-context.tsx` keep one store under `dayform.settings.v1` (groups: profile name, accent, new-task defaults, notifications, greeting, calendar window / week start / 12h-24h, habits, widget, updates). `useSettings()` works without a provider. The Personal tab renders `PERSONAL_SECTIONS` (`components/personal/sections.tsx`); add a card there. `constants/accents.ts` applies one of 6 accent sets over the palette (`useColors()` already does it; a contrast test pins every set). `NamePrompt` asks for the name once. **Categories are data-driven** (`lib/categories*.ts`, key `dayform.categories.v1`): the four built-in ids (`Focus`, `Work`, `Personal`, `Wellness`) never change so stored tasks need no migration; custom ids are `c_xxxxxxxx`; `Category` is a plain `string`, so never index a record by `task.category` (use `resolveCategory` / `useCategoryColors().get(id)`; unknown ids fall back to "Other"). Custom and renamed names are user content and are never translated. Deleting a category moves its tasks first (not undoable) and only then removes it. Categories travel in backups, recovery copies and snapshots as an optional `categories` field. **Habit hints** (`lib/habits*.ts`, `components/habits/`) derive duration / category / repeat suggestions, focus hours and long-waiting tasks from the user's own tasks; one switch gates them and nothing leaves the device. The **Android widget** is an Expo module in `modules/dayform-widget/` (Kotlin), fed by `lib/widget-syncer.ts`; it shows only the data the app sends and can hide titles. It is offered in two picker sizes, 4×2 (`TodayWidgetProvider`, declared 280×120 dp) and 4×3 (`TodayWidgetProviderLarge`, a subclass with its own `dayform_widget_info_large.xml`), which share one renderer; `WidgetUpdater.updateAll` must cover both. **Widget background picture** (Widget section of the Personal tab, `components/personal/WidgetBackgroundSection.tsx`): the user picks an image with expo-document-picker; the native `WidgetBackground.kt` copies it (shrunk to 1280 px, upright, JPEG) into the app's private `filesDir` and draws it per widget at the size the launcher reports (cropped to fill, rounded to the card's 24 dp corners, plus a white veil of 0..90 %, 72 by default, so the dark task text stays readable; over a picture the grey texts (date, durations, done rows) use the darker `*_photo` colours and every text has a soft white glow from `android:shadowColor` in the layout) into the first `ImageView` of `dayform_widget.xml` (RemoteViews bitmap, longest side capped at 900 px). The picture and its veil live only natively (`WidgetStore` prefs), not in the settings, backups or snapshots; the veil is never sent in the widget snapshot. **The widget follows the Theme page's accent** (not its light/dark scheme: the card is always light): `lib/widget-accent.ts` takes the light `primary` and `primaryTint` of the chosen accent set and `lib/widget-snapshot.ts` sends them as optional `ac: { p, t }` (`#rrggbb` only; absent for an older app, and the widget then keeps the orange of `res/values/colors.xml`). `WidgetRenderer` paints text colours with `setTextColor` and tints the badge, progress fill and next-row background / bar with `setColorStateList` (API 31+); `WidgetUpdater` applies the views once and falls back to plain colours (`tints = false`) if a launcher cannot apply the tints. **RemoteViews only inflates allowed classes**: a plain `<View>` (or `layout_*` attributes left outside a tag) makes the launcher show an endless spinner with nothing in logcat, so use `ImageView` for decorative bars, and read the `DayformWidget` log tag, where `WidgetUpdater` applies the views once and logs why they cannot be applied. **Widget pet** (Pet settings page with a picture card per pet, `components/personal/PetPicker.tsx`: the picked pet walks through its frames, copied to `assets/pets/<art>/walk_N.png` and listed in `lib/pet-images.ts` because Metro cannot reach the native drawables, so a new pet or frame needs both copies; `settings.pet = { kind, walks }`, `lib/pet.ts`, sent to the widget as `pet` / `petWalks` in the snapshot, both optional natively): a launcher cannot animate a RemoteViews, so `WidgetPet.kt` fills a `ViewFlipper` with one child per frame (`RemoteViews.addView` of one of 41 layouts `dayform_pet_frame_00..40`, generated files where two empty `ImageView` spacers share the free width by weight, so the pet's place is a fraction of the real width: a launcher can report a stale or too small width after a resize, and a dp padding then keeps the pet from the right edge; only the height above the bottom is a dp padding), building a random 48-second script of poses (walk, run, sit, look, bark, jump, sleep; the mood of the day picks the weights) (the art only walks and runs sideways, so a trip changes height by at most 35% of its length and bobs with each step, and an art that has `walk_d` / `walk_u` frames (kitsune and chicken: facing the viewer / seen from behind) uses them for trips straight down / up (half of the trips when the roaming area is at least 16 dp tall; with under 100 dp of room below the rows the pet roams the whole card body, over the rows, so a 4-row widget still has about 100 dp to walk up and down in); every loop also touches both edges, stops there to look around, and straight up/down trips only start at least 30 dp from the edges; a jump uses the front-facing `bark` pose when the art has one, and any pose held within 30 dp of a side edge faces away from it, since a sideways run-jump in place against the wall read as ramming it) from the drawables `dayform_pet_<art>_<set>_<l|r>_<n>` (kept from shrinking by `res/raw/dayform_keep.xml`; a pose the art lacks falls back to a similar one). Only the chosen pet's frames are inflated. **vivo reports the widget 25 dp narrower than it draws and counts the app label in the height**, so `WidgetRenderer` corrects for it (measured: 297x213 dp drawn, 272x242 reported); other launchers get no correction. **vivo ignores `targetCellWidth/Height`** and floors `(declared dp + 40) / 80` into cells (its own widgets declare 120 dp for 2 cells and 280 dp for 4), so the declared minimum must be an exact `80n - 40`: 4×2 is 280×120 dp and 4×3 is 280×200 dp (250×180 was placed as 3 columns). **Goku Black pet** (a fan pixel sprite sheet of a Dragon Ball character, author not recorded, no licence, included at the owner's request; every character-sized frame of the sheet is cut out into 192 px drawables by scripts that are not kept in the repo) plays a fixed film instead of a stroll, `GokuPet.kt`: a table of `Seg`ments (a set of frames, where it moves along the card, lunge, shake, arc, per-frame flash, hit-stop frames) in six scenes that repeat whatever the mood, about 158 ticks (~47 s; one tick = one flip = 300 ms; `hold` slows a segment, and the loop must not pass the 160 ticks of the other scripts, so a slower scene needs a shorter one elsewhere): start (stances, blurred frames, grey aura), combo (dash behind speed lines, punches, uppercuts, jump, spinning kicks, a blue-skinned opponent made by swapping red and blue is thrown back, lies down, is dizzy), charge (turn away, growing ball, first black beam, spirit-bomb pose, shaking aura, flash), transformation (bow, red eyes, flash, hair turns white, blue aura, zoomed sprite, white stances), finisher (white-haired fight, big ball, thin then big beams, explosion, recoil) and end (aura calms, stance, victory poses). Frames are `dayform_pet_goku_<set>_<n>` (the art faces right). A launcher cannot shake a screen or zoom a camera, so the shake is the sprite jittering and the zoom a bigger sprite; **white flashes are a second full-card `ViewFlipper` (`dayform_widget_fx`) that flips in step with the pet**: `WidgetPet.Frame.fx` picks one of the `dayform_fx_flash_*` layouts per tick, and only a script that sets an `fx` adds the layer. `walk`, `sit` and `sleep` (with `_l_`/`_r_` sides) stay only for the pet test and the Pet page preview. **Paimon pet** (a Live2D fan model of a miHoYo character, rendered offline into frames, no licence; included at the owner's request) floats, so it has its own script, `PaimonPet.kt`, instead of the walking one in `WidgetPet.kt`: it drifts freely up and down, keeps a hover bob and plays its own poses (dayform_pet_paimon_<set>_<n>, 21 sets from the model's 20 motions; only `walk` has `_l_`/`_r_` sides, mirrored). `sit`, `sleep` and `walk` must stay, since the pet test requires them for every art. The pixel pets are CC0 art by Shepardskin (OpenGameArt cat sprites and dog sprites; the gray cat is recoloured, the original is black and vanishes on the dark card; the orange cat was removed at the owner's request, and a stored `orange-cat` now resolves to the default `gray-cat`); the credit is shown on the Pet page. Never write the words "cycle", "menstr" or "fertil" in widget files (a privacy test scans them), so call a sprite loop a "stride". **Keyboard:** screens are edge-to-edge, so Android does not resize them for the keyboard. `SettingsPage` (like `TaskEditor`) pads its scroll content by `useKeyboardInset()` and scrolls the focused field above the keyboard with `useRevealFocusedInput` + `RevealOnFocusProvider` (`components/editor/reveal-context.ts`): a new settings field must call `useRevealOnFocus()` in its `onFocus`. Transparent Modals (the assistant's `ChatSheet`) pad themselves by the keyboard height on Android; `KeyboardAvoidingView` with `behavior={undefined}` does nothing there. A settings page floats its add button through `components/menu/floating-action.tsx` (`useFloatingAction`), not inside the scrolling card.

**Assistant Leo** (`components/assistant/AssistantOverlay.tsx`, mounted after `UndoBar` in `_layout.tsx`; its own Personal page **Assistant** (`components/personal/AssistantSection.tsx`, menu slug `assistant`) holds `settings.assistant.enabled` (**on by default**), `name` (what it is called, default "Leo"), the voice and the AI chat; hidden on `/cycle`): an original chibi character (leopard hoodie) supplied by the owner. The pure core is tested: `lib/assistant-state.ts` (states idle / greeting / listening / thinking / talking / angry / happy / sleepy / dragged, the owner's transition diagram, one-shot durations, tease = 4 taps in 1.5 s, sleepy after 2 min without a touch), `lib/assistant-pose.ts` (per-frame transforms) and `lib/assistant-answers.ts` (three preset questions answered **on the device** from today's tasks; titles are user content, passed as `{placeholders}` and never translated; strings in `lib/i18n/assistant.ts`). Without the AI chat, "listening" is the question menu being open. **AI chat** (`settings.ai`, **off by default**): the user brings an **OpenAI-compatible** provider (`baseUrl`, default `https://api.openai.com/v1`, https only except a server on the local network; `model`; `shareTitles`), and the **API key lives only in `expo-secure-store`** (`lib/ai-key-expo.ts`; the plugin runs with `configureAndroidBackup: false` so the app's own backup rules stay and the key is never backed up). Tapping the assistant then opens `ChatSheet.tsx`; `use-ai-chat.ts` wires the pure, tested core: `ai-stream.ts` (SSE + UTF-8 across chunks + tool-call deltas, or a whole JSON answer), `ai-config.ts`, `ai-prompt.ts` (system prompt + a compact list of today's tasks; titles only when shared), `ai-loop.ts` (tool rounds, at most 6) and `ai-tools.ts` (20 tools, "full rights" at the owner's request: reads (`list_tasks`, `get_settings`, `list_special_days`) run at once; every change is **shown on a confirmation card and runs only after the user agrees** (the owner's choice): `create_task` / `edit_task` / `move_task` go through the task editor's own `planSave` (reminder 0/5/15/30/60 min, repeat rule and end date, status, backlog, category, notes, and the series scope this/following/all checked with `allowedScopes`), `delete_task` through `planDelete` with a scope, `complete_task`, `reopen_task`, bulk `complete_tasks` / `delete_tasks` (≤30), all as one `mutate(..., { undo: "bulk" })`; plus `update_settings`, `set_language`, `add_category` / `rename_category`, `add_special_day` / `delete_special_day` and `undo_last`; `CARD_TEXTS` lists every card line and a test checks each is translated). Every argument is checked with zod and a failed check goes back to the model as an error; `update_settings` only touches the open groups (`OPEN_SETTINGS`: never `ai` (a hostile task title must not be able to point the base URL elsewhere), the period tracker, backups, imports or recovery) and refuses a value the settings schema would replace. `ai-client.ts` posts `{baseUrl}/chat/completions` with `expo/fetch` (React Native's fetch cannot stream). The AI's words go into the speech bubble as a `{reply}` value so they are never looked up in the dictionary. **Voice input** (`expo-speech-recognition`, i.e. Android's own recognizer; on the owner's vivo phone that is Speech Services by Google, `com.google.android.tts`, listed with the Google app in the plugin's `androidSpeechServicePackages`; `RECORD_AUDIO` comes from the plugin): `settings.assistant.wakeWord` (**off by default**; turning it on asks for the microphone) makes `components/assistant/use-voice.ts` listen continuously for the name while the app is in front and the assistant is idle or sleepy (it pauses whenever the assistant talks or works, so it never hears itself, restarts after the recognizer's silence timeout, and stops for good on a permission / service / language error), then takes one sentence. `lib/voice-command.ts` (tested) recognises "{name} ơi", "hey/ê/này {name}" accent-insensitively and keeps a question said in the same breath, a spoken yes/no for the confirmation card (no-words win; "dạ" is left out because without marks it is "đã"), a preset question when the AI chat is off, and "cảm ơn"/"thôi"/"bye" that end the exchange. A spoken exchange goes on by voice: after the answer the assistant listens again until silence or a goodbye, and a change the AI wants is read out ("… Shall I?") and answered by voice or by a tap. **Every session names its recognition service** (`chooseRecognizer`: the phone's default if set, else Google's `com.google.android.as` / `.tts` / Google app; never another app's recognizer): the owner's vivo has no default selected and Android then ends every session at once (`no selected voice recognition service`), which looked like a blinking microphone. A wake session that ends within 1.5 s without hearing anything counts as a failure and the restart waits 0.3 s doubling up to 30 s; after 5 in a row listening stops and the assistant says it cannot use the microphone. Speech Services by Google (`com.google.android.tts`) recognises **offline only** and fails with `language-not-supported` until its language pack is downloaded; the same service is then asked again **without** `EXTRA_PREFER_OFFLINE` (it recognises on Google's servers), and only after 3 network tries that still end that way is it skipped for the locale (`languageMissing`); a network try started right after the previous session gets `MICROPHONE_UNAVAILABLE` (the microphone is not released yet), falls back to offline and reports the missing pack again, so a session after a missing-language answer waits `LANGUAGE_RETRY_MS` (1.5 s). The owner's vivo exposes no other recognition service (the Google app offers none to other apps; the Claude app's is never used), and Speech Services' Vietnamese *voice* data (`superpacks/vi-vn`, for speech output) is not a recognition pack. **Never call `androidTriggerOfflineModelDownload` without `supportsOnDeviceRecognition()`**: on a phone without Android's on-device recognizer (the vivo) the library calls `createOnDeviceSpeechRecognizer` on the main thread and the app crashes; the download button opens `com.android.settings.TTS_SETTINGS` there instead (Google's own language-pack screens are not exported). **Never start a session with `continuous: true`**: on Android 13+ expo-speech-recognition then records the microphone itself and passes the audio to the service through `EXTRA_AUDIO_SOURCE`, which Speech Services by Google cancels at once ("#startListening received from a caller without permission android.permission.RECORD_AUDIO") even though the app holds the permission; listening for the name is a chain of ordinary sessions that restart when one ends. **Speech to text with Soniox, in real time** (`lib/soniox-rt.ts`, tested; `components/assistant/use-soniox.ts` glue; the Soniox API key lives only in `expo-secure-store` like the AI key, entered on the Assistant page and checked with `GET https://api.soniox.com/v1/models`): `expo-audio`'s `useAudioStream` (16 kHz mono int16) is streamed as binary frames over React Native's WebSocket to `wss://stt-rt.soniox.com/transcribe-websocket` (key in the `Authorization: Bearer` header through RN's third WebSocket argument, which the web typings lack; first message the config: `stt-rt-v5`, `pcm_s16le`, the real sample rate, `language_hints`, endpoint detection with `max_endpoint_delay_ms` 1000). Provisional tokens show live, final ones accumulate, and the final `<end>` token closes an utterance; an empty text frame ends the stream. **"once"** (holding the assistant, release sends; the chat's microphone, a second tap sends; at most 30 s; dragging drops it) takes one sentence. **"listen"** replaces the phone's recognizer for the call by name when a Soniox key exists: it streams while the app is in front, the chat is closed and the assistant is idle or sleepy, and stops after any problem until the switch is turned on again; **Soniox charges for that streaming time**, which the Assistant page says. Without a Soniox key the phone's recognizer is used as before. Problems (no key, microphone, Soniox's error, network) are shown in the chat or said by the assistant. The `expo-audio` plugin runs with `enableBackgroundPlayback: false`. Holding the assistant or the chat's microphone takes one sentence without the name. Offline recognition is preferred (`EXTRA_PREFER_OFFLINE`); without the language's offline pack the recognizer may send audio to Google, which the Assistant page says next to a button that asks the recognizer to download the pack (`voice-expo.ts`, untested glue). **Speech** (`settings.assistant.voice`, on by default, switch on the Greeting page): `expo-speech`, i.e. the phone's own text-to-speech engine; `lib/assistant-speech.ts` (tested) picks a voice of the app's language only, prefers an on-device (`local`) one over a `network` one, and stays silent when there is none rather than reading Vietnamese with an English voice; the user can pick one of the language's voices, each row with its own play/stop button for a sample (`components/personal/AssistantVoicePicker.tsx`, `settings.assistant.voiceId`, "" = automatic). Vietnamese keeps the natural pitch (a raised pitch made it sound squeezed), and `speakableText` rewrites what is said, not what is shown ("1/3" → "1 trên 3", "09:45" → "9 giờ 45", ellipses → a pause). expo-speech can only use the phone's default engine: the owner's vivo phone ships only vivo's own engine (`com.vivo.aiservice`), which reads Vietnamese poorly, so the picker tells the user to install Speech Services by Google and make it the preferred engine; it also estimates a syllable timeline (one syllable per Vietnamese word) that drives the talking bob now and is meant for `ParamMouthOpenY` later. The answer ends when the engine reports it finished (with a fallback timer); greetings and reactions are spoken but end on their own timers. Leo is silent while a screen reader is on (the bubble is read instead), and drag, leaving the app, a tap while talking or switching the voice off stop the speech (`assistant-speech-expo.ts`, untested glue). Until the Live2D model is rigged it is the flat picture `assets/assistant/leo.png` moved by transforms (hover, tilt, bounces, shake and turning away, a tilt against the drag, a bounce when let go; smaller with the system's reduce-motion), and the animation loop stops while the app is in the background. The Live2D package (`leo.model3.json`, physics, 6 expressions, 12 motions, README with the rig plan) lives outside the repo and still lacks `leo.moc3` and its textures; when they exist, only the picture layer should change. **Holidays, lunar dates and special days** (`lib/lunar.ts`, `holidays-vn.ts`, `day-marks.ts`, `special-days*.ts`, `special-reminders.ts`, `special-day-draft.ts`, `hooks/use-day-marks.ts`, `components/personal/SpecialDays*.tsx`): `lunar.ts` is the Vietnamese lunar calendar (Hồ Ngọc Đức algorithm, UTC+7, years 1900..2100); lunar day 30 clamps to 29 in a short month and a leap-month special day uses the regular month. `holidays-vn.ts` marks Vietnam's solar and lunar holidays only as marks (never claims a "day off"; Tết days 1-3 have `showDate:false`). `day-marks.ts` merges holidays and the user's special days (theirs first) for the week strip (flag = holiday, heart = special day), the day header and the widget; the settings are `calendar.showHolidays`, `holidayGroups` and `showLunar`. Special days (birthday, wedding anniversary, memorial/giỗ, custom; yearly on a solar or lunar date, optional start year giving "turns N") live under `dayform.special-days.v1` with the same store/context shape as categories (`useSpecialDays()` works without a provider) and travel in backups, recovery copies and snapshots as an optional `specialDays` field (a file with special days but no tasks is still a valid import). Reminders exist only for the user's own days (`remind`: none / day-before 08:00 / same-day 08:00), use id prefix `dayform:special:` and share the 50-notification budget: `taskReminderLimit(summary, cycle, special)` = 50 − 7 − 6 − 8 (`SPECIAL_MAX_REMINDERS = 8`, horizon 60 days); with "hide titles" on, the text is one neutral line. User-written titles are never translated and are replaced by the generic "Special day" on the widget when titles are hidden. The widget snapshot carries optional `m` (up to 2 names, 40 chars) and `sp` (1 = a user's special day) per day; the Kotlin renderer shows the `dayform_widget_marks` line (costs `MARKS_DP` of rows and pet room) and the pet cheers on a special day. Tooling pitfalls seen here: a Perl regex with `\|` or `\u` inside a replacement corrupts files (use Edit or sed `#`), and a day that has marks but no tasks still appears in the widget snapshot with `n: 0`.

**Cultivation (experience and ranks, `lib/realm.ts`, `xp.ts`, `xp-store.ts`, `xp-sync.ts`, `xp-context.tsx`, `rank-label.ts`, `ladder-words.ts`; `settings.xp = { enabled, sound, style }`, on by default, style `cultivation` or `engineer`):** **Two styles share one experience total (owner's request):** `LADDERS` in `realm.ts` has `cultivation` (9 realms Luyện Khí … Độ Kiếp, stages sơ / trung / hậu kỳ, đại viên mãn; 324 steps; each stage 40 x 1.5^realm) and `engineer` (5 ranks Intern, Fresher, Junior, Middle, Senior, stages Alpha / Beta / RC / Stable; 180 steps; each stage 40 x 2^rank); `rankOf(total, ladder)` and the other ladder functions default to cultivation, and the penalty floor, the demotion and the rank-up are all judged on the ladder in use (`useXp().ladder`), so switching style changes only names and pictures, never points. `ladder-words.ts` maps each cultivation English key to its engineer wording (`word(style, key)`; "breakthrough" becomes "promotion", "experience" becomes "XP"); every wording and the key it replaces must be translated in `lib/i18n/realm.ts` (a test checks it). The Personal menu row is the neutral "Rank", its page has the style picker. **Badges are drawn, not stored (owner's request, to keep the APK small):** only the main picture of each rank (the emblem) is an image, `assets/ranks/emblems/<style>-<track>.png` (about 4 KB each: the first five cultivation realms and the five engineer ranks, listed in `constants/rank-emblems.ts`; a PNG cannot be `require`d by `bun test`, so `rank-art.test.ts` reads that table as text and checks every file exists). Everything else (the round or hexagonal background, the rings that grow with the stage, the diamonds, glow and rays of đại viên mãn / the rivets, glow and circuit lines of Stable, the nine pips or bits of the layer, the bars or tick of the stage) is drawn from Views by `components/cultivation/RankBadge.tsx` from the shape list that the pure `lib/rank-art.ts` produces in a 256 x 256 space (geometry ported from the generators of the original icons; `PALETTES` has the colours of all 9 realms and 5 ranks; a rank without an emblem yet, cultivation realms 6 to 9, gets a generic glowing orb). Shapes are plain data, so a script can draw the same list as SVG to preview a badge without a phone. The emblems were cut out of the generators' SVG with `sharp` (the scripts are not kept in the repo): to add the emblem of a new rank, extract its centre picture the same way, add a `require` to the table and nothing else. finishing a task earns experience once; the rank is never stored, only derived from the total (`rankOf`): 9 realms (Luyện Khí … Độ Kiếp) x 9 layers x 4 stages (sơ / trung / hậu kỳ, đại viên mãn) = 324 steps, each stage costing 40 x 1.5^realm (a multiple of 5). **Entering the next great realm is a bottleneck (owner's request):** after layer 9, perfection, the cultivator must gather `breakthroughCost(realm)` = 15 stages' worth more before the next realm begins; meanwhile the rank stays at layer 9, perfection, with `rank.breakthrough = true` (the step count does not move, then rises when the realm is entered), and the last realm has none. `goalLine` says what is missing (the next stage, the start of the breakthrough, or the breakthrough itself) and `toNextRealm` the whole road to the next realm. The ledger lives under its own key `dayform.xp.v1` (never inside a task, so an older build cannot damage it; same read-lock / corrupt-copy / serial-queue rules as the categories store). `claimed[taskId]` makes the points per task: finishing again earns nothing and undoing a completion takes back exactly what it gave. **Where it is hooked:** `createTasksStore(storage, { onCommitted })` reports every successful write, `xp-sync.ts` diffs the lists (finished = newly done, reopened = done before and not now; a task that leaves the list keeps its points) and `TasksProvider` calls `claim` / `revoke`; **a write that moves data, not a deed, must pass `noXp: true`** (import, archive, restore do; a new bulk path that rewrites tasks must too, or it would pay out experience for every done task in it). **Rules that must not regress:** a task planned for a day already over when it was created (made today for yesterday, `isLateAdded`) earns nothing and is not a day of work, so nothing can be backfilled for points or to dodge a penalty; a task ticked within 2 minutes of its creation earns a quarter; per-task experience is `duration x 40 / 60`; **experience is time, 40 an hour (`XP_PER_HOUR`), and a day has a finite supply (owner's rule): at most 19 hours of work count (`MAX_WORK_HOURS`, so 5 hours of rest are always left), i.e. `DAILY_CAP` = 19 x 40 = 760 per day, bonuses and streak included, and no single task is capped on its own (a very short task still earns at least 5)**; done on the planned day x1, backlog x0.8, past x0.6, future x0.5; a streak of 3 / 7 / 30 active days multiplies by 1.1 / 1.25 / 1.5. **Rest days (owner's rule):** a day without any finished task is judged once it is over (`settleDays`, run by `XpSettler` at start, on resume and every 10 min): it is a free rest day while the week (Monday start) has fewer than 1 and the month fewer than 4, and resting keeps the streak; after that it costs 40 x the number of penalised days in a row (cap 5 steps) and resets the streak; the first two cannot push the total below the start of the current realm, the third in a row can (a demotion); a day of work clears the chain; overdue tasks are never penalised; after a long absence only the latest 14 days are judged. The assistant announces what judging the days found (`xp-notice.ts`: a penalty, a demotion or a rest day; waits until it is idle so it never talks over the greeting). The UI is the Personal tab's `ProfileCard` (the rank badge takes the frame before the name; under the name come the rank and a short "20/40 exp" line, `expLine`: what is gathered of the current stage over what it takes, plus a thin bar; tapping either opens the `cultivation` settings page; with the system off the old initial avatar shows). The `cultivation` settings page has the style picker, the rank, the style, today (n / 760), streak, rest days left, the realm strip, every rank of the current realm, the two switches and "start again".  **Sound:** `assets/sounds/rank-step.wav` (a new stage or layer) and `rank-realm.wav` (a new realm) are synthesised bell tones played by `rank-sound-expo.ts` (expo-audio, untested glue); the assistant plays one and says the congratulation when `useXp().lastGain.rankUp` changes (`settings.xp.sound`). Pure modules are tested; the screens are not.

**Period tracker (health data, `lib/cycle*.ts`, `components/cycle/`, `app/cycle.tsx`, key `dayform.cycle.v1`):** local only, off by default, never in the widget, OTA/update requests, logs or error reports. Pure core: `cycle.ts` (ops + merge, re-exports `cycle-model`/`cycle-parse`), `cycle-predict.ts`, `cycle-calendar.ts`, `cycle-stats.ts`, `cycle-lock*.ts`; store/context mirror categories (`useCycle()` works without a provider). **Safety rules that must not regress:** the "safe days" output is a calendar-method ESTIMATE, never contraception, shown only from a run of ≥3 consecutive recent cycles (a gap outside 15..60 days resets the run), never when late, irregular, paused or stale, never for projected future cycles, never on the Timeline, and always worded as "lower-risk (low confidence)" with a disclaimer next to the legend. Standard Days = cycle days 8..19 (lastStart+7..+18), Ogino = shortest−18 / longest−11. **Privacy rules:** the lock (`expo-local-authentication`, in-memory unlock window, locked at cold start) guards the screen AND export/import/restore of cycle data (`use-cycle-auth`, `cycle-lock-guard.ts`); `expo-screen-capture` blocks screenshots and the recents thumbnail on the cycle screen; a replace import never changes the current `lock`/`acknowledged`/`enabled`; "Delete all cycle data" (`cycle-purge.ts`) also strips the tracker from snapshots and safety copies, removes `dayform.cycle.corrupt.*`, and cancels `dayform:cycle:*` notifications; notifications are discreet (title "Dayform", neutral body, private channel `cycle-v1`, no data payload so a tap only opens the app) and share the 50-notification budget with task reminders and the morning summary (`reminders-plan.ts`). The exported backup file is NOT deleted right after sharing (the receiving app may read it lazily); it is removed at the next start or export.

**Network:** two calls of the app itself, both without task data, plus the AI chat when the user turns it on. (1) The APK update check (`GET https://api.github.com/repos/dainn-dev/dayform/releases/latest`, at most every 12 h); only `https://github.com/dainn-dev/dayform/` URLs are ever opened. To ship a new APK publish a non-prerelease GitHub Release tagged `vX.Y.Z` (equal to `expo.version`) with the APK attached (see `RELEASING.md`). (2) Over-the-air content updates (`expo-updates`) from `https://dayform-updates.pages.dev` (platform, runtime version and expo-updates' own device id are sent). One switch in Settings turns both off; one button checks both (`lib/update-summary.ts` merges their status). (3) The AI chat (off by default): the question, the conversation, today's tasks (titles only with `ai.shareTitles`) and tool results go to the base URL the user configured, with the user's own key; nothing else is ever sent there and the period tracker never is. (4) Soniox (only with a Soniox key): the microphone is streamed to `wss://stt-rt.soniox.com` while the user holds the assistant or uses the chat's microphone, and, with "Call by voice" on, the whole time the app is open and the assistant is idle; the key check calls `https://api.soniox.com/v1/models`.

**Over-the-air updates:** only JavaScript, assets and strings can ship this way. Kotlin, permissions, icons, `app.json`, a new native library or an Expo SDK change need a new APK (bump the version and tag). `runtimeVersion` follows `expo.version` (policy `appVersion`), so an update only reaches the APK with the same version, and the site serves one runtime at a time. `checkAutomatically` is `NEVER` and `fallbackToCacheTimeout` is 0: startup never waits for the network; `lib/ota.ts` (+ `ota-expo.ts`, `ota-context.tsx`, `OtaAutoCheck`) downloads in the background (throttled to every 12 h) and the update applies on the next launch; nothing ever calls `reloadAsync`. Updates are signed: the certificate `packages/mobile/ota/certs/certificate.pem` is public and embedded in the APK; the private key is NOT in the repo (`~/.dayform-signing/ota/`, CI secret `DAYFORM_OTA_PRIVATE_KEY`). `packages/mobile/ota/` turns an `expo export` into a static site (signed manifest, content-hashed assets, `_headers`) and verifies it; the manifest must carry the app config in `extra.expoClient` or `Constants.expoConfig` is empty (the installed version would read 0.0.0). Publish with the manual **OTA update** workflow, or locally: `DAYFORM_OTA_PRIVATE_KEY_PATH=... bun ota/publish.ts --base-url https://dayform-updates.pages.dev --runtime-version <expo.version> --out ../../ota-site`, then `wrangler pages deploy ota-site --project-name dayform-updates`. OTA data changes must stay backward compatible: an older bundle rewrites storage and zod drops fields it does not know.

**All task data is device-local via AsyncStorage; there is no backend call in the product path.**
- Tasks live under key `dayform.tasks.v1`. `lib/tasks-store.ts` is the framework-free store (the tested core); `lib/tasks-context.tsx` is only a thin `useSyncExternalStore` wrapper over it, and `useTasks()` is its public API. Invariant: **a slow, failed or corrupt read must never lead to the stored array being overwritten.** So: writes wait for the initial load, the new list is computed *inside* a single serial queue from the last committed list, and writes are pessimistic (state changes only after `setItem` succeeds; no optimistic update or rollback). A failed read locks writes; if only some records are bad and their copy fails, the store is read-only.
- `lib/task-storage.ts` (`loadTasks`) validates records with a Zod schema, and never writes the main key. Invalid records go to `dayform.tasks.corrupt.<hash>` and unparseable data to `dayform.tasks.backup.<hash>` (content-addressed keys, so repeated launches don't pile up copies). Zod strips unknown fields, so a field added in a newer version is lost if an older build rewrites the data. First launch seeds `seedTasks()` from `lib/planner.ts`.
- `lib/timeline-layout.ts` (`layoutLanes`) assigns side-by-side lanes per cluster of transitively overlapping blocks, using a minimum visual duration matching the 38px minimum block height. The "⚠ Overlap" label is driven by real `overlaps()`, not by lane count.
- `lib/language.tsx` owns the EN/VI switch under `dayform.language.v1`, separate from tasks. It holds the Vietnamese dictionary and exposes `t(text)`. **The English string is the dictionary key**, so a missing translation silently falls back to English; add every new UI string to the `vi` dictionary. User-entered titles/notes and stored category ids must never be translated.
- `lib/planner.ts` has the `Task` model and pure date/time helpers. Dates are local wall-clock `YYYY-MM-DD` strings, times are `HH:mm`, durations are integer minutes, and weeks start Monday. Do not use UTC or `toISOString()` for task dates. `date`/`start` are `null` for backlog tasks. Tasks cannot cross midnight. `overlaps()` drives the conflict warning, which warns but can be overridden on save.
- Timeline spec (06:00–22:00, 64px/hour, side-by-side overlapping blocks, outside-hours list) and the visual tokens are in `design.md`. Colors come from `constants/theme.ts` and `categoryStyle` in `planner.ts`.

`metro.config.js` adds the workspace root to `watchFolders` and `nodeModulesPaths`. Without it, hoisted dependencies don't resolve.

`app.json` has the deep-link scheme `dayform`, the DAINN splash (white wordmark on a full-screen `#6565E8` background; Android 12+ only supports a centred logo on a flat colour) and adaptive/monochrome icons, and bundle ids `com.dayform.hpxhrm5k` (Android and iOS; randomly generated, changing it makes Android treat the app as a different app and loses its local data). Unused storage/overlay permissions are blocked in `app.json`. **Android Auto Backup is on, but only for AsyncStorage's one SQLite database and only when the backup can be end-to-end encrypted** (`plugins/with-backup-rules.js`: `dataExtractionRules` with `disableIfNoEncryptionCapabilities`, `fullBackupContent` with `requireFlags="clientSideEncryption"`; pinned by `plugins/with-backup-rules.test.js`). Backup rules work on files/databases, never on single keys, so **everything in AsyncStorage rides along, including the period tracker and the recovery copies**; that is why the user-facing privacy sentences say "stays on this device (and in your phone's encrypted backup, if it is on)" and must not go back to "never sent anywhere". Nothing else is backed up (no expo-updates cache, shared preferences or exported files). If cycle data ever has to stay out of the backup, move its storage out of AsyncStorage first. Do not store secrets or tokens in AsyncStorage. Release APKs are signed with the private release key (`plugins/with-release-signing.js`, see `RELEASING.md`); a local build without the `DAYFORM_*` environment falls back to the debug key. **Version rule (owner's request): every time a change is built into a new APK, bump the patch version by one** (`expo.version` 1.0.1 → 1.0.2 …) **and `android.versionCode` by 1** in `app.json`; `packages/mobile/android/app/build.gradle` is generated, so also update its `versionCode`/`versionName` if you build without re-running prebuild.

### Web/API template (`packages/web`)

API features are oRPC procedures, one file per feature in `src/api/routes/`, composed into `router` in `src/api/index.ts` and served at `/api/rpc/*` (health at `/api/health`). `src/api/__core/app.ts` is template-managed. `bun run lint` enforces a 500-line cap on each `routes/` file. Drizzle config and scripts (`db:generate|migrate|push`) read the root `.env`.

### Fixed contract with Runable

The root script names (`dev`, `dev:desktop`, `dev:mobile`, `build`, `start`, `stop`, `lint`, `typecheck`, `db:*`) are used by deployment tooling and must keep their names. Ports come from `.runable/ports.json` via `__ports.cjs` and are fixed for the app's lifetime. Don't change them, since each preview URL derives from them. Secrets go in the root `.env`, and browser-exposed values need the `VITE_` prefix.
